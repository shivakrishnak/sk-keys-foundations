A junior engineer who does not know these numbers cannot reason about system performance: a design that makes 10 “cheap” database calls may unknowingly introduce 5ms of latency per request (10 * 500us for network + query). 🔥 The Problem This Solves

In 2009, Jeff Dean and Peter Norvig circulated a table titled “Numbers Every Engineer Should Know” within Google. The numbers described the characteristic latency of every major operation in a computing system: L1 cache access, DRAM access, SSD read, HDD seek, network packet round-trip. The table was simple: each row was one type of access; each value was one number (rounded to the nearest order of magnitude).

Why did this table become one of the most shared engineering documents in history? Because engineers constantly make design decisions without knowing the latency of the operations they chain together. A database query over the network includes: application code (nanoseconds), network latency (500us), database query (microseconds), disk read if cache miss (100us for SSD). If an engineer knows only “it’s one database call,” they may call it 10 times and add 5ms to every request.

The latency table forces engineers to:

  1. Know the cost of every operation type they use
  2. Count how many times each operation is performed per request
  3. Estimate the total latency budget before writing code
  4. Identify the dominant latency contribution (the bottleneck)

This is the mental model that separates engineers who write fast systems from engineers who write slow systems and then wonder why.

📘 Textbook Definition

Latency numbers every engineer should know is a reference table (originally from Jeff Dean, 2009) listing the characteristic access latency for each level of the computing system hierarchy. The values are order-of-magnitude estimates (accurate to 1-5x) rather than exact measurements, because they vary by hardware generation and specific configuration. The table is used as a mental model for system performance estimation: an engineer multiplies operation counts by characteristic latencies to estimate total latency budgets. The hierarchy roughly doubles in access time per level, with occasional order-of-magnitude jumps (DRAM to SSD: ~1000x; SSD to HDD: ~100x; same-datacenter network to cross-datacenter: ~20-50x).

The pattern: each major tier change (cache -> DRAM -> SSD -> HDD -> network) represents 100-1000x latency increase. The network entries show why distributed systems are inherently slower: even within the same availability zone, network RTT is 5000x slower than DRAM.

⚙️ Why It Holds True (Formal Basis)

Why the hierarchy exists and why the ratios are stable:

Cache to DRAM (100x latency ratio): L1 SRAM is on the same die as the CPU, 1-2 mm from the ALU. Signal propagation time + sense amplifier time: ~1 ns. DRAM is 5-50 mm from the CPU (on a DIMM across traces on the motherboard). Signal must travel off-die: ~5 mm * 0.1ns/mm = 0.5 ns propagation, plus DRAM row access physics (tRCD ~15 ns

  • tCAS ~15 ns): total ~30-100 ns. The physical distance and DRAM access physics are the cause; both are limited by physics.

DRAM to SSD (1000x latency ratio): DRAM access is electronic (charge a capacitor: ~100 ns). NVMe SSD is flash storage: reads require charging floating- gate transistors and reading voltage levels. Flash read latency is limited by: (a) NVMe protocol overhead (PCIe command processing: ~10 us); (b) NAND flash cell read time (~25-50 us); total: ~100 us = 1000x DRAM.

SSD to HDD (100x latency ratio): SSD read is electronic (no moving parts): ~100 us. HDD read requires: rotational latency (disk spins to right sector: 7200 RPM = 8.3ms average rotational latency) + head seek (move read head: 5-15ms). Total: 5-20ms = 100-200x SSD.

Network to DRAM (10,000x latency ratio): Even within the same data center rack, a network packet must: serialize (64 bytes at 10 Gbps = 51 ns), travel through switch fabric (2-5 hops: each hop 1-5 us), be received by kernel, be demultiplexed by OS and handed to application. Total: 50-500 us. vs DRAM: 100 ns. Ratio: 500-5000x.

These ratios are stable across hardware generations because they are determined by: (a) physics (speed of light, RC delay); (b) protocol overhead (PCIe, Ethernet). Protocol overhead decreases over time (DPDK, RDMA reduce kernel network overhead) but physics limits apply.

1. Latency budgeting in system design

EXAMPLE: API request latency budget

Target: p99 < 50ms

Step 1: Identify operations per request
  - Business logic: 1ms (CPU, in-memory)
  - Cache lookup (Redis): 1ms (network + DRAM)
  - Database query (if cache miss): 5ms (network + NVMe read)
  - External API call (payment): 30ms (WAN, P99)

Step 2: Multiply by call count
  - Cache: always 1 call = 1ms
  - DB: 10% miss rate * 1 call * 5ms = 0.5ms expected
    (P99: if 1% of requests have 5 cache misses: 25ms)
  - External API: always 1 call = 30ms

Step 3: Sum for critical path
  Expected: 1 + 1 + 0.5 + 30 = 32.5ms OK
  P99 path: 1 + 1 + 25 + 30 = 57ms > 50ms TARGET MISSED

Step 4: Fix P99 path
  Option A: pre-warm cache to reduce miss rate
  Option B: async external API call (deferred response)
  Option C: increase P99 target to 100ms for this request type

2. Amdahl-style latency dominance analysis

For each request type, identify the latency-dominant operation. The dominant operation determines what optimization is useful:

If dominant operation is:
  Network call (>1ms): reduce call count or use RDMA
  DRAM access (>100ns * many accesses): cache or prefetch
  SSD read (>100us): increase DRAM cache hit rate
  CPU computation: optimize algorithm or SIMD

Optimization in the WRONG layer wastes effort:
  Optimizing CPU computation from 5ms to 1ms does not help
  if an uncached external API call takes 50ms.
  Always optimize the dominant latency source.

Latency measurement: calibrating the numbers for your hardware

"""
Benchmark: measure actual cache/DRAM/SSD latency
on your hardware. Compare to reference values.
"""

import ctypes
import os
import random
import time
import struct
from pathlib import Path

def ns_now() -> int:
    """Return current time in nanoseconds (CLOCK_MONOTONIC)."""
    return time.monotonic_ns()

def measure_cache_dram_latency(size_bytes: int) -> float:
    """
    Pointer-chasing benchmark. Measures latency per access
    for an array of given size.
    Returns average ns per access.
    """
    # Build a random permutation of indices (pointer chase)
    n = size_bytes // 8
    indices = list(range(n))
    random.shuffle(indices)

    # Encode as C array for low overhead
    arr = (ctypes.c_uint64 * n)(*indices)

    ITERS = max(1_000_000 // n, 100)  # total ~1M ops
    idx = 0
    start = ns_now()
    for _ in range(ITERS * n):
        idx = arr[idx]
    end = ns_now()

    return (end - start) / (ITERS * n)

def measure_ssd_latency(path: Path) -> float:
    """
    Measures random 4KB read latency from a file.
    Returns average us per read.
    """
    file_size = 256 * 1024 * 1024  # 256MB test file
    tmp = path / "latency_bench.bin"
    try:
        if not tmp.exists():
            with open(tmp, "wb") as f:
                # Write 256MB of random data
                for _ in range(256):
                    f.write(os.urandom(1024 * 1024))

        with open(tmp, "rb") as f:
            results = []
            for _ in range(1000):
                offset = random.randrange(0,
                    file_size - 4096) & ~4095  # 4K aligned
                f.seek(offset)
                t0 = ns_now()
                _ = f.read(4096)
                t1 = ns_now()
                results.append(t1 - t0)

        return sum(results) / len(results) / 1000.0  # -> us
    finally:
        tmp.unlink(missing_ok=True)

    """Print measured latency vs reference table."""
    print("\nMeasured vs Reference Latency Table:")

⚠️ Common Misconceptions

Misconception 1: “These numbers are too imprecise to be useful.” Reality: The purpose is not exact measurement but order-of- magnitude reasoning. Knowing that DRAM is ~1000x slower than L1 cache is sufficient to decide: “my data structure should fit in L2/L3 for this inner loop.” The exact numbers matter for performance tuning (measured by profiler); the order-of- magnitude numbers matter for design-time decisions (before writing code). Design-time decisions have 10-100x higher leverage than post-hoc optimization.

Misconception 2: “Network latency is predictable; I can ignore variance.” Reality: the table shows median (P50) latency; P99 and P999 can be 10-100x higher due to: network congestion, switch buffer overflow, kernel scheduling jitter, GC pauses (in JVM services), and tail latency in distributed services. A system designed around P50 network latency will violate SLAs for 1% of users (P99 10x worse = 5ms -> 50ms; exceeds 10ms SLA). Always design with P99 in mind; multiply by a conservative 2-10x buffer for P99 vs P50.

Misconception 3: “Jeff Dean’s original numbers are still accurate in 2024.” Reality: The original 2009 numbers have changed significantly: (a) DRAM latency is now ~70-100 ns (same order; DDR5 is similar latency to DDR3 despite higher bandwidth); (b) SSD is now NVMe at ~100 us (vs SATA SSD at ~200 us, vs HDD at 10ms in 2009; HDD is nearly obsolete for primary storage in data centers); (c) network latency has improved: DPDK and RDMA enable sub-100us in-datacenter network for specialized use cases. The table structure is stable; specific values need updating. Use the 2024 reference table in this entry.

🚨 Diagnostic Signals

DS1: Service latency spikes during business hours. Network or storage contention: network latency from P50 to P99 increases under load. Diagnosis: plot latency histogram at different times. If P50 stable but P99 increases: tail latency is the issue (network queue depth, GC pause, disk seek contention). Use the latency table to identify which tier is expanding: add tracing (OpenTelemetry) to measure per-operation latency in production.

DS2: Database query is fast in testing but slow in production. Common cause: test environment has data in L3 cache (small dataset); production has cache misses (large dataset, random access pattern). Diagnosis: check database buffer pool hit rate. If <90%: queries are hitting disk. At NVMe SSD latency (100us) * number of disk reads per query = total query time. Fix: increase buffer pool size or add caching layer.

DS3: gRPC service calls consistently add 5-10ms unexpectedly. DNS resolution not cached: each gRPC call resolves the service hostname via DNS before connecting. Uncached DNS lookup: 20-100ms. If DNS resolution is per-connection (not per service), this adds to every call. Diagnosis: add DNS resolution timing to telemetry. Fix: use connection pooling (resolve DNS once per pool, reuse connection); or use service mesh (Envoy sidecar handles service discovery locally without DNS).

🎯 Interview Deep-Dive

Q1: You are designing a URL shortener service. For the read path (redirect), what operations are needed and what is the expected p99 latency? How would you design for a 10ms p99 SLA?

A: The URL shortener read path needs: (1) receive HTTP request; (2) look up short code -> original URL; (3) return 301 redirect.

Step 1: Identify operation latencies:

  • HTTP request parsing: ~1 us (in-process, CPU-bound)
  • Database lookup (if not cached): ~5-10 ms (PostgreSQL with index, NVMe disk if cache miss)
  • Cache lookup (if Redis): ~1 ms (network + DRAM)
  • HTTP response write: ~1 us

Step 2: Latency budget analysis: Without cache: 1us + 5-10ms + 1us = ~5-10ms P50. P99 with disk misses: potentially 50ms+. Exceeds 10ms SLA.

With Redis cache (hot redirects): 1us + 1ms + 1us = ~1ms P50. P99: 1ms (Redis) + 2ms (GC jitter) = ~3ms. Within 10ms SLA.

Design for 10ms p99 SLA:

  1. Put all active URL mappings in Redis (TTL = time to live for URL shortener links, e.g., 24 hours). This eliminates DB for hot redirects.
  2. Use Redis pipeline or Lua script to combine the GET + TTL refresh in one round-trip (~1ms vs 2ms for two calls).
  3. Cache DB results for cold URLs (LRU cache with 10M entries in Redis = ~800MB) - covers long tail of infrequent URLs.
  4. P99 analysis: 99% of traffic hits Redis cache (~1ms); 1% hits DB (5-10ms); P99 = 10ms. Exactly the SLA.
  5. For P999 (<0.1% traffic hitting DB on cache miss): add read-through to DB with SSD storage (not HDD); ensure connection pool pre-warmed; measure actual P999 in production.

The latency table drives the design: Redis is the only operation that fits in a 10ms P99 budget for a cache-miss-tolerant workload.

🌍 Sustainability & Ethics

The latency table is a sustainability tool as well as a performance tool. Operations at higher latency tiers consume more energy: an NVMe SSD read (100us) consumes far more energy than a DRAM access (100ns) for the same data. A network packet round-trip (0.5ms) involves NICs, switches, kernel drivers, and application processing on both ends - an order of magnitude more energy than a local DRAM access. Engineers who apply the latency table to reduce the number of network calls per request (from 50 to 5) do not just reduce latency - they reduce energy consumption by a similar factor. At the scale of Google processing 8 billion searches per day: reducing the number of network hops per query by one saves an amount of energy comparable to removing a small power plant from the grid. The latency table is therefore an energy efficiency tool: designing systems that minimize operations at higher-latency (higher-energy) tiers is both faster and more sustainable. Engineers who understand the table’s implications make greener systems as a byproduct of making faster systems.
